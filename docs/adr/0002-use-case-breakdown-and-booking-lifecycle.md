# ADR 2: Деталізованість прецедентів та розподіл життєвого циклу бронювання

## Контекст і постановка проблеми
Під час переходу від моделі даних до функціональних вимог постало питання визначення меж ключових сценаріїв: об'єднувати вибір місць, замовлення послуг та оплату в один монолітний Use Case чи розділяти їх на окремі прецеденти зі зв'язками include та extend. Окремо необхідно було вирішити, як моделювати 15-хвилинне холдування місця без блокування основного потоку.

## Розглянуті альтернативи
1. **Альтернатива 1**: Створити один загальний Use Case «Придбати квиток», де всі кроки (пошук, вибір крісла, вибір багажу, списання коштів, відправка квитанції) виконуються як один неподільний процес.
2. **Альтернатива 2**: Розбити процес на окремі прецеденти: базовий процес «Бронювати квиток» обов'язково включає «Вибрати місце» (`include`), опціонально розширюється замовленням послуг (`extend`) та скасуванням за таймаутом (`extend`), а транзакція оплати виноситься в окремий пов'язаний прецедент «Оплатити замовлення» із залученням зовнішнього банку.

## Рішення
Обрано **Альтернативу 2**.  
Це повністю відповідає життєвому циклу сутностей у базі даних: бронювання може існувати у статусі `PENDING` окремо від оплати (клієнт зафіксував місце, але має 15 хвилин на введення реквізитів картки). `extend` для додаткових послуг гарантує, що клієнт не зобов'язаний купувати багаж чи харчування, а відхилення за таймаутом є альтернативним сценарієм (відокремленим).

## Наслідки
* **Позитивні**:
  * Пряма узгодженість із моделлю даних (поля `Booking.expires_at`, `FlightSeat.status`, сутності `Payment` та `TicketExtraService`).
  * Простота тестування сценаріїв у Gherkin (кожен крок тестується окремо без довгих ланцюжків передумов).
  * Чітка ізоляція взаємодії із зовнішніми системами (Payment Gateway, Notification Service).
* **Негативні**:
  * Збільшення кількості прецедентів на діаграмі (8 замість 2-3), що вимагає підтримки більшої матриці трасування.
